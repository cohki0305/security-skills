# セキュリティ診断スキル 設計書

2026-10-24 作成

## 1. 何のためのものか

中小企業（IT 企業ではない一般企業）が、自分たちのセキュリティが今どのくらいのレベルかと、次に何をすればいいかを知るための Claude Code スキル。

- YouTube 動画の**特典として無料で配る**。販売はしない。配布者のサポートなしで、受け取った企業が単独で使い切れることが前提。
- 使う人は、すでに Claude（Claude Code）を使っている人。デスクトップアプリの Code タブでも、ターミナルの CLI でも動くこと。
- 対象 OS は Windows と Mac の両方。
- 完璧な診断は目指さない。「自社の現状と、次にやることがわかる」ところまでを目標にする。手に余る所は、結果の中で「ここから先は専門家や業者に相談」と正直に書く。

### Cowork ではなく Claude Code にした理由
Cowork は PC 本体から切り離された仮想マシンの中で動き、許可したフォルダしか見られない。そのため、ウイルス対策・暗号化・OS 更新などの PC 本体の設定を読めない。社員にコマンドを手で貼ってもらう案は、相手の社員には無理と判断した（依頼者の判断）。

## 2. ゴール・やらないこと・失敗とみなすこと

**ゴール**
- 担当者が質問に答えるだけで、会社全体の診断レポートが出る
- 社員が自分の PC で動かすと、PC の設定を実際に読んで結果ファイルができ、それが会社の診断に集まる
- レポートは「事故の場面ごと」に、今の状態と次にやることを示す（見本の A 案）

**やらないこと（今回の範囲外）**
- 設定を直すこと。PC の設定は読むだけで、一切変更しない
- 継続的な監視。定期的な再診断の通知も今回は作らない。ただし、前回と比べられるよう結果ファイルは保存しておく
- ISMS 監査や認証の代わりになること
- 配布者側のサーバーへのデータ送信。すべて相手の PC の中で完結させる

**失敗とみなすこと（動いても失敗）**
- **診断の道具そのものが事故の入口になる。** Claude がその場で考えたコマンドを実行する、設定を変える、個人のファイルを読む、など
- 形骸化する。具体的には次の 3 つ（依頼者が特に気にしている点）
  1. 「入っているか」だけを見て、中身を見ない
  2. 会社ごとの違いを拾えず、その会社で一番危ない所が抜ける
  3. 質問への答えが「はい」ばかりになり、実態とずれる
- 答えられない質問で詰まり、最後まで進めない
- レベルを安全の保証と受け取られる書き方になる
- 社員が監視されている、評価に使われると感じる書き方になる

## 3. 全体の形

1 つのスキルの中に 2 つの使い方を持つ。

| 使い方 | 誰が動かすか | 何をするか |
|---|---|---|
| 会社の診断 | 経営者・総務・情シス担当 | 質問に答える。社員の PC 結果を読み込む。会社全体のレポートを出す |
| 自分の PC の診断 | 社員一人ひとり（担当者自身も） | PC の設定を読む。本人向けの短い結果と、担当者に渡す結果ファイルを出す |

### 最初に聞くこと（人に合わせる）
起動したら、最初に次の 2 つを聞く。
- 立場：経営者／総務・情シス担当／一般社員
- IT にどのくらい詳しいか（3 段階程度）

答えに合わせて、質問の数、言葉の難しさ、結果の書き方を変える。
- 経営者：事故の場面と、業務・お金・信用への影響を中心に短く
- 担当者：具体的な設定手順や確認方法まで
- 一般社員：自分の PC でやることだけ

一般社員を選んだ場合は、自動で「自分の PC の診断」に進む。

## 4. PC のチェック（部品の棚）

### 原則
- **Claude はその場でコマンドを考えない。** スキルに同梱した読み取り専用スクリプト（以下「部品」）だけを実行する。
- 部品は項目ごとの小さなスクリプトにする。Windows は PowerShell、Mac はシェル。
- **どの部品を使うかは、質問の答えから Claude が選ぶ。** 例：「VPN は〇〇を使っている」と答えたら VPN の部品を足す。ただし選べるのは棚にある部品だけ。
- **部品だけを確認なしで動かす。** スキルの `allowed-tools` で部品の実行だけを許可し、確認画面が出ないようにする。社員に何でも「はい」を押させる流れを作らない。利用者の Claude Code の設定（settings.json の deny やフック）は書き換えない。部品以外のコマンドは、Claude Code の普段どおり確認画面が出る状態のままにする。スキルの指示でも、部品以外を実行しないよう明記する（Claude の判断：「設定を変えない」約束を優先した）。
- **「最新か」「サポート切れか」の基準は同梱の表で判断する。** 診断中にネットは見ない。表には作成日を持たせ、レポートに「基準表：2026-xx-xx 時点」と出す。表の更新は GitHub で配り直す（Claude の判断）。
- **「有無」ではなく「鮮度・中身」を読む。** ウイルス定義の更新日、最後のスキャン日、OS の最終更新日、暗号化の有無と回復キーの保管先など。
- **個人のファイル、閲覧履歴、メールの中身は読まない。** 出力に個人情報（個人のファイル名など）を含めない。部品の出力は Claude（Anthropic）に送られるため。
- **管理者権限を求めない。** 管理者権限がないと読めない項目は「わからない（管理者権限が必要）」として結果に出し、担当者への確認事項に回す。
- 同じ PC なら毎回同じ結果になること（再現性）。

### 最初にそろえる部品（目安 15〜20 個・事故の多い順）
最終的な一覧は実装者が決める。最低限、次のものを含める。
- ウイルス対策ソフト：動いているか、定義の更新日、最後のスキャン日（Windows は Defender と他社製の両方）
- ディスク暗号化（BitLocker / FileVault）：有無、回復キーの保管先がわかる範囲
- OS の更新：最終更新日、保留中の更新
- ファイアウォール：オン／オフ
- 画面ロック：自動ロックまでの時間、パスワードの要否
- OS のサポート期限：サポート切れの OS ではないか
- ローカルの管理者アカウント：普段使いのアカウントが管理者か
- リモートデスクトップ・画面共有：外から入れる設定がオンになっていないか
- VPN ソフト：入っているか、最新か（質問で使っていると答えた場合）
- クラウド同期（OneDrive / Google ドライブ / Dropbox 等）：どれが入っているか（会社が認めていないものの把握用）
- ブラウザ：更新されているか

### 社員の結果を会社に集める方法（Claude の判断）
- 社員の PC 診断は、結果ファイル（例：`PC診断_山田_2026-10-24.json`）を作る。
- 社員はそのファイルを、普段の手段（メール・チャット・共有フォルダ）で担当者に渡す。
- 担当者は受け取ったファイルを決まったフォルダに置く。会社の診断を動かすと、Claude がそれを読み込んで集計する。
- 未確認の台数を出すため、会社の診断の質問で PC の台数を聞く。
- **Claude Code を使っていない社員の PC は対象外。** 「未確認」として台数に数えるだけにする（依頼者の決定）。点検ファイルを配る、担当者が代わりに動かす、といった別の道は作らない。

## 5. 会社への質問

### 原則
- **選択式。** Claude Code の選択式の質問機能を使う。
- **どの質問にも「わからない」を必ず置く。** 「わからない」は失敗ではなく、それ自体が結果になる。「誰も把握していない」は、それだけで直す対象として、責めない書き方で結果に載せる。
- **「あとで確認」も選べる。** 保留した質問は「業者や担当者に聞くことリスト」にまとめ、聞き方の文面も付ける。答えがわかったら、その質問だけ答え直せる。
- **まず簡単に聞き、大事な所だけ深掘りする。** 最初は「している／していない／わからない」で聞く。「している」と答えた重要な項目だけ、「最後に戻せるか試したのはいつ？」「退職日の何日後に止めた？」のように事実で 1 段深く聞く。全部の質問を深掘りしない（答えられない人が出るため）。
- **スクリーンショットは任意。** 重要な所で「管理画面のスクリーンショットを貼れるなら」と頼み、貼られたら Claude が読む。貼らなくても進める。社員の氏名が写りやすい項目（退職者アカウントなど）は、まず「何件か」を数で答えてもらう質問にする。レポートと聞くことリストには個人名を書かない（Claude の判断）。
- **答えに応じて質問が分岐する。** 使っている SaaS（Google Workspace / Microsoft 365 / 会計・人事 SaaS など）、VPN の有無、NAS やサーバーの有無、テレワークの有無などで、聞く内容と使う部品を変える。

### 質問の範囲
質問の元ネタは、IPA の「中小企業の情報セキュリティ対策ガイドライン」と「5 分でできる！情報セキュリティ自社診断」を基本にする。項目の選定と文面は実装者が作る。最低限、次の領域を含める。
- アカウント管理（退職者、共有アカウント、2 段階認証）
- バックアップ（どこに、何世代、戻せるか試したか）
- メール（乗っ取り対策、誤送信）
- 使っている SaaS と、その管理者
- 社外からのアクセス（VPN、リモートデスクトップ、テレワーク）
- 社内ネットワーク（Wi-Fi の分離、NAS）
- 事故のときの連絡先と手順
- 社員への教育

## 6. 結果レポート（A 案：事故の場面ごと）

見本：https://claude.ai/artifact/3p37w4B9EqrhSirBzm9XEG の「A 事故の場面ごと」

- **出力先**：相手の PC にローカルの HTML ファイルとして出し、ブラウザで開く。あわせて、診断データを JSON で保存する（次回との比較用）。
- **上から順に**
  1. 会社名・診断日・確認した PC の台数（全体の何台中何台か）
  2. 全体のレベル（A〜E）と、それが何を意味するかの 1 文。「目安で、安全を保証するものではない」と必ず書く
  3. 事故の場面ごとのカード。状態は「危ない／一部危ない／わからない／守れている」の 4 つ。各カードに、今の状態の説明と「次にやること」を書く
  4. 未確認の PC の台数と、社員に PC 診断を回してもらう案内
- **場面の例**：ランサムウェアに感染したら／辞めた人のアカウント／PC をなくしたら／メールが乗っ取られたら／外から社内に入られたら／ウイルス対策／OS の更新。最終的な場面の一覧と、質問・部品との対応は実装者が決める。
- **立場で書き方を変える**（3 章）。社員本人向けの結果は、自分の PC の場面だけを短く出す。
- **別ファイルで出すもの**
  - 業者や担当者に聞くことリスト（「わからない」「あとで確認」の項目と、聞き方の文面）
  - PC ごとの結果一覧（担当者向け）。会社のレポート本体には台数だけを出し、個人名は出さない（Claude の判断。社員に監視と感じさせないため）

### レベルの決め方
- **決まったルールで計算する。** 毎回 Claude の感覚で決めない。同じ答えと同じ PC の結果なら、必ず同じレベルになること。
- 例：重大な場面（ランサムウェア、退職者アカウントなど）に「危ない」が 1 つでもあれば上限を C にする、など。具体的なルールは実装者が作り、スキルの中に表として持つ。

## 7. 書き方の決まり
- 顧客向けの文章なので、専門用語を避け、業務で何が変わるかで書く。
- 「〜を押すと進みます」のような自明な説明は書かない。
- 社員を責める書き方をしない。「わからない」や「未対応」は、会社として直す対象として書く。
- 日本語の文章は natural-japanese スキルの基準に合わせる。

## 8. 配布
- GitHub か zip で配り、Claude Code にスキルとして入れる。手順は README 1 ページにまとめる（Windows / Mac それぞれ）。
- README に必ず書くこと
  - 何を読み、何を読まないか。設定は変えないこと
  - 読んだ内容は Claude（Anthropic）に送られること。会社で使うなら法人プランの Claude を推奨すること
  - 診断は目安で、安全を保証するものではないこと
  - 社員に PC 診断を頼むときの案内文のひな型（何を読むか、結果を誰が見るか）

## 9. 実機での確認
- **Windows**：開発用の Windows PCで、実装者が部品を実行して確かめる。
- **Mac**：依頼者が手元の Mac で試す。実装者は、Mac で試す手順と、何を見ればよいかのチェックリストを用意する。
- 両方で、管理者権限のないアカウントでも「わからない」だらけにならないことを確かめてから配る。

## 10. 実装者に任せること
- スキルのファイル構成、部品の書き方、結果 JSON の形
- 部品の最終一覧と、Windows / Mac それぞれでの読み取り方法（管理者権限なしで読める方法を優先）
- 質問の一覧と文面、分岐の作り方
- 場面の一覧と、質問・部品との対応表
- レベル計算のルール
- HTML レポートの見た目の作り込み（見本の A 案に沿う）
- スキル名（仮：`security-checkup`。Claude の判断）

## 11. 今回は作らないが、あとで足すかもしれないもの
- 前回の診断との比較表示（データの保存だけは今回やる）
- 定期的な再診断の通知
- 直す手順をスキルの中で案内する機能（設定の変更そのものは今後もしない）
